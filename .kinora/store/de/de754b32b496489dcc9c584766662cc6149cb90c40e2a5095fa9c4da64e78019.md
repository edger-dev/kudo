# Spec — an agent harness owns the worker's CLI-specific integration

**Chosen.** The worker engine talks to an **agent harness** boundary. The engine
keeps contexts, claims, leases, submissions, queue order, and turn decisions; a
harness owns the agent CLI's executable and session mapping, launch argv and
environment, configuration or plugin artifacts, permission and MCP loading,
startup and takeover conventions, and hook payload and reply translation.
Claude Code and Kimi Code are the first two harnesses. A later harness, such as
OpenCode, implements the same boundary without changing the worker engine.

The launch description carries configuration artifacts as well as argv and
environment: a harness that needs files or an installed plugin cannot be
represented honestly by command-line flags alone. Capabilities that differ are
named and tested rather than assumed. A harness that cannot provide a required
capability must say so before launch; it must not stub or imitate it.

**Why.** The current launch plan and hook replies are Claude Code's protocol.
Substituting another executable therefore fails before the worker loop starts,
and conditionals around that plan would couple every consumer to every CLI's
flags, configuration, and lifecycle. An explicit adapter leaves the context and
lease semantics single-source and lets each harness keep its own model.

**Rejected.** An executable-name switch around Claude Code's flags. A
lowest-common-denominator hook protocol, which would discard useful harness
capabilities. Separate pull loops per CLI, which would let claims, submissions,
and takeover semantics drift.

**Escape hatch.** A harness may offer only a headless or only an interactive
worker while the other mode is being built, but the limitation is explicit in
its capability report and documentation; it is never presented as full support.
Each harness runs the shared conformance tests, and the real-CLI end-to-end
checks exercise its advertised modes.
