# Plan — v1: the first working kudo in nine phases

**Task:** kino://4aef99814b668f7cbb8900eee43e35b67fdb6dbcd18ba196858f6226874cc0e2

Six phases over six weeks, two weeks of slack, starting 16 Oct 2026;
re-planned 22 Oct (kino://bdb04ec6f96900d0cca5440747a4cb73feb85af2f39b7a5331a3b0b91ac4b116) to nine, so the
dogfood week has recurring, waiting, cross-host work to run: process control,
due-dated checks and the phone console come before it. Every
phase is cut so one night session can finish a step and leave the ledger
committed (`kinora store` → `kinora commit` on main → `git commit`), because
the next session starts cold and may be driven from a phone. A phase that
needs two sessions still ends each one that way.

The design notes of 15–16 Oct (inbox, `note-*`) refine every phase below with a
"Plan delta" list; fold a note's deltas in when its phase opens.

The order is tracer-bullet first: nothing is built that the end-to-end path
does not exercise, and the console lands early enough that each later phase
is reviewed by watching it, not by reading diffs.

## Phase 1 — a worker pulls (week 1–2)

The loop is decided: kino://b9ef8909cadf0092e9b9d01eb3fc3edbe9db4f2af17f80753571d9434628b1af (from the 16 Oct pull-worker-loop
note). This phase builds it against the real CLI.

- The shim gains MCP tools `context_read`, `pull`, `submit` and `inbox`,
  plus hook subcommands in the same binary. Dry-run first, as the earlier pull
  tools were.
- `kudo-node` starts a worker as the interactive agent CLI in a terminal pane
  (the job substrate's terminal lens), under a context id and a repo path from
  the context's declaration, passing the worker settings file and the MCP
  config on the command line.
- SessionStart binds and injects the head; Stop hands over the next item of the
  same context, or lets the session end on one of the four lease-end
  conditions; the open-claim guard refuses a stop without a submit.
- Claims are write-once kinos with a deadline; an expired claim is re-pulled as
  attempt N+1.
- Observe: the node tails the CLI's transcript and relays it as events; the hook
  events (pull, submit, takeover, lease end, compaction) are the loop's own
  trace. A submission is a write to the context, never a parsed transcript.
- Done when: two consecutive items of one context are worked as two turns of
  one session; each of the four lease-end conditions ends a session once; a
  killed worker's item is re-pulled after its deadline.
- Open: claim deadline length and whether a worker may extend its own claim
  (heartbeat from PostToolUse); budget accounting from the hook's usage fields
  or from turn counts.

Status: in progress (20 Oct). Built and tested (78 tests): the queue over a
local kinora store (claims with deadlines, races resolved by forks), the hook
decisions, `kudo-shim hook <event>`, the worker tools `context_read` /
`pull` / `submit` / `release`, the launch plan, and `kudo-shim worker`
(the CLI as a worker in the current pane). End to end against the real CLI
in print mode: two items of one context worked as two turns of one session,
the second through the Stop handoff, both in the head and the log. The runs
added two rules, now in the spec: the guard gives up after three refusals, and
one item per turn is enforced.

Live since (print mode): a turn budget of one ends the lease as budget with
the third item left for the next lease; a worker killed mid-item has its item
re-pulled as attempt 2 by the next worker once the deadline passes; the
`inbox` tool files a line with its lease (80 tests).

21 Oct: installed by the home module on yolo, and the author ran a worker
interactively in a pane and reported it working. `kudo-shim context list`
added (every context newest first, with its counts), and every command takes
a unique prefix of a context id.

22 Oct: confirmed in panes launched from the node through the console, on
pc's yolo and edger's (phase 4, step 5–6), waiting for work between items.
Left: the two lease ends not yet seen live (a human prompt, a compaction).

## Phase 2 — the context kino (week 2–3)

- The `context` kino shape: resume block (where / next / established / open),
  log, repos, queue. Submissions rewrite the block and append the log.
- Queue items are kinos too, write-once, with a state that moves by append.
- A context names repos per node; starting a worker in a repo under a
  context is one call that resolves node + path from the declaration.
- Done when: two workers in two repos on one node submit into one context.

Opened 21 Oct. Decided (author, 21 Oct): a submit from a moved head is refused
(kino://3a472b4021f7b7496dd37779f3d0c76cafe1c95e8e80b1b236786a81e4c7d0ab);
evidence is kino ids (cite-and-cache from repo ledgers) and URLs, spans wait
for phase 3
(kino://4e67251bc978f34e7d6ce4278eb1503f9e803e51f0057d4d5954c701830f22b9); the
repos declaration is its own kino
(kino://b53b7abd832f2cd0e58e5084f5733af5d56f762c52cd6fd404913911920a6de9). The
context-unit amendments of the 16 Oct note were already in its current
version. Steps, each a test/impl/review cadence:

1. A context's card is unique (inbox: one title, one second, one context).
2. Moved-head refusal: the claim records its head; a fork closes on the next
   submit.
3. The typed submission: established / claimed / ruled out / gaps / head;
   evidence check and downgrade; the body rendered in sections.
4. The repos kino: `context repo add`, `worker <ctx> --repo <name>` on this
   node; cite-and-cache from a declared repo's ledger.
5. The hook trace: pull, submit, takeover, lease end, compaction as kinos of
   the lease.
6. Live: two workers in two repos on one node submit into one context.

Status: done (21 Oct). All six steps built test-first, each reviewed by a
fresh reviewer and fixed in its own commit:

1. A context's card carries a random marker.
2. Moved-head refusal; the claim shows the head it records (handoff and
   pull); head versions carry a writer marker, so a head returning to earlier
   text never loops the history, and a fork always closes; every tip is shown
   (spec v2).
3. The typed submission: established / claimed / ruled out / gaps; evidence
   resolves to the context's own cited kinos or earlier submissions, or an
   http(s) URL with a host — never the queue's own records; free text cannot
   forge a section (spec v2).
4. The repos kino: `context repo add`, `worker <ctx> --repo <name>`;
   cite-and-cache from a declared repo's ledger; a raced declaration loses
   no repo.
5. The trace (kino://a6751902e8e01e5d7d5983196da9170f33f40d0d74246b5746977ea1c5e45098):
   lease start, handoff, pull, refused stop, release, submit, lease end as
   write-once kinos; `context trace`, and `context why` traces a head
   forward to its submission, claim, item and lease.
6. Live (print mode, real CLI): two workers started at once in two repos on
   one node (`--repo a`, `--repo b`) under one context. B submitted first; A
   was refused for the moved head, folded B's decision in and resubmitted.
   The final head holds both decisions, each established with its repo's
   kino resolved by cite-and-cache; the trace shows both leases; `why` names
   A's submission, claim, item and lease.

Carried: transcript spans as evidence and in the forward trace (phase 3);
tool-call counts and files touched as trace events (PostToolUse, when
needed); the refused submit is not a trace event yet; `why` names the
submission that wrote a head, so a submit that left the head unchanged is
reached through the trace, not the head; a submit or release is refused for
a claim another lease took; every store read loads
the whole store — fine at this size, an index is phase 3's.

## Phase 3 — the store moves to the object store (week 3–4)

- In **kinora**: an S3-compatible backend for a store, content-addressed and
  write-once, cited from the reachability spec here. Its task lives in the
  kinora ledger: `kinora:c650f51df78e4018da6bb0ec59a22aa08d52708167f3490e3194f9cd67d2383c`.
- kudo points the context store at it; project `.kinora/` ledgers stay on git.
- Done when: the phase-2 scenario runs with the laptop node asleep for one
  of the two workers, and the console (phase 4) later reads it from a phone.

Opened 21 Oct. Decided (author): Cloudflare R2; credentials as sops secrets
in the dotfiles; the work in kinora. Shape: a mirror, not a storage rewrite —
kinora-remote pushes and pulls a store's write-once files (put-if-absent,
verified on pull, remembered sends), and kudo's context store syncs at every
read and write
(kino://fc473f56b1b8bdbae4a31e54e7281c4aeed3c08bd03804b256ca37e1937fe66f).

Status: in progress (21 Oct). Built and reviewed (two rounds, all fixed):
kinora-remote (`s3://`, `file://`, `memory://`; S3 gives up in seconds) and
the mirrored context store (claims re-checked against the mirror, offline
backoff, refused credentials an error, lease-checked submit and release).
Live with the real CLI: two workers on two separate stores sharing only a
`file://` mirror — one was refused for the head the other moved and folded
it in; both stores end with the same head and trace. R2 live (21 Oct): bucket
`kudo-contexts`, an Object Read & Write token scoped to it, as a sops secret
that pc and edger decrypt and push into their yolo (`kudo-r2-push`; yolo has no
age key), read by kudo-node and the console as an EnvironmentFile. pc's store
uploaded (46 s once, then ~0.5 s a read); a worker on edger's yolo built its
store from R2, claimed and submitted an item of "my first context", and pc's
store shows the submission and trace. Left for the done-when: the same with
one host's node asleep, and the console read from a phone. (The "starting
forever" finding is resolved by stale panes, kino://0c4e36f264b2b4fbc6fcfee93bc02ad5b8419a1d21a8638bf080623ab942a37d.)

## Phase 4 — the console (week 4–5)

- Dioxus SPA, a direct hub consumer: nodes → contexts → workers → transcript;
  enqueue an item; "take over" shows how to attach to the pane.
- Shell patterns rewritten from the two earlier consoles: multi-host, per-node
  modules, one shared reading pane. No code ported.
- Done when: the tracer bullet runs from the console on two nodes; and a
  second arrangement of the same panes is produced by changing the layout
  value only (16 Oct console note).

Opened 21 Oct. Decided (author): **Dioxus fullstack** — a native console
server links the context engine and the hub client, the browser calls it
(console spec re-versioned; direct-from-browser S3 is the escape hatch for a
phone while everything sleeps); the server is **run by hand** until the views
settle; **moco is fixed first** so a node can start a real interactive worker
pane; live updates ride a **hub event channel**, built now. Three panes
(where / head / trace) under the note's four rules (a pane is
render(kind, resolve(query)); the arrangement is one value; renderers keyed
by kind; selection is one state value). Steps, each test/impl/review:

1. moco: an ad-hoc start carries an environment and a human view (terminal),
   so a worker pane is launchable through the hub (moco's ledger).
2. hub: an event channel — publish one event, subscribe to a stream (hub's
   ledger); the one hub revision v1 needs.
3. kudo: the loop's events (enqueued, claimed, submitted, lease start/end)
   published by whoever writes them, when a hub is reachable.
4. kudo: the console crate — server functions over the engine and the hub,
   the layout value, the three panes, enqueue.
5. kudo: start a worker on a node and take it over, from the console.
6. Live: the tracer bullet from the console on two nodes; a second
   arrangement by changing the layout value.

Status: done (21 Oct). Steps 1–3 done, each reviewed and fixed:
1. moco (`moco:2f25a32ffd97b45f10b5168f99d65001e07fd5339e524eabde6b45716fc08680`):
   an ad-hoc start carries env and a terminal view (a governed node refuses
   env; the reply says what was applied); a terminal job accepts input —

2. hub (`hub:3cd8fac90600281adadd0aeb3fc25c74eac2e9690587c8fc9ad4334d6e6ad955`):

3. kudo: every traced loop event and every enqueue is published, best

kudo pins hub 828a6b0 and moco b08ac94. The deployed hub on pc must be rebuilt
before the console sees events there.
4. (21 Oct, built; review pending) kudo-console, Dioxus 0.7 fullstack: one
   layout value (THREE_PANES; STACKED by value alone,
