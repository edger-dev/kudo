# Design note, 16 Oct 2026: the object-store backend in moco

Baseline: moco today is the cell/function framework; the byte substrate RFC-0005 assigns to it does not exist — phase 3 builds it from nothing. kinora's on-disk layout defines what it must carry.

## What kinora writes, and what each needs

| Write | Shape today | Backend need |
|---|---|---|
| content object | `store/<2hex>/<hash>.{md,styxl,jsonl}` | put-once, get, exists |
| ledger event | one file per event, set-union mergeable | put-once, one-level list by prefix |
| root pointer | `roots/<name>`, swapped by tmp+rename | the only mutable write today |
| compaction output | a new root kinograph version, byte-deterministic | put-once |
| transcript blob (new) | tens of MB | multipart put, hash computed before upload, dedupe by exists |

## Decisions

1. **Backend contract = five write-once calls**, the one the orchestrator proved with fs + in-memory backends: get, capped get, put-once, exists, container/one-level children. put-once on S3/R2 = conditional put (If-None-Match) — verify R2's precondition support in phase 3 before relying on it.
2. **Root pointer is append-only** (YJ, 16 Oct): `roots/<name>/<ts>-<hash>`, write-once, latest by listing. No compare-and-swap anywhere. Two concurrent compactors → two heads (kinora already represents multiple heads); the next compaction resolves via `parents[]`. Forks not locks, consistently. Rejected: CAS on one key (a lock in disguise, a sixth call, provider-dependent).
3. **Shape in moco:** one substrate crate (RFC-0005): the backend trait; an fs backend carrying kinora's current layout unchanged; an in-memory backend for tests; the S3 backend. kinora depends down on it; identity/metadata stay in kinora.
4. **Per-node working memory = a cached backend**, fs in front of S3, read-through, write-through put-once. Pull-before-start / push-at-submit are the cache's sync, nothing more.
5. **Index without a database.** The root kinograph version compaction already builds (entries with inline metadata) *is* the index of a root. A reader fetches one object (current root version) + lists one short prefix (hot events since). The phone does two calls. Rebuild = a walk ("the index is a derived projection"). No SlateDB-style LSM on S3 (what an earlier prototype needed; kinora does not).
6. **Compaction on an object store:** no branches, only the event prefix; any writer may compute the next root version from (hot events, prior version); byte-determinism means two writers produce the same object and put-once dedupes it.

## Plan delta

- Phase 3 = the substrate crate (trait + fs + mem + S3 + cached), kinora pointed at it, the append-only root pointer in kinora's store layer (fs backend gets it too — layout change, one-time migration of `roots/<name>` to `roots/<name>/<ts>-<hash>`), the context store on R2, transcript blobs as the first large objects. Done when (sharpened): the phase-2 scenario runs with the laptop asleep for one worker; two compactors run concurrently and the store ends with one root version; the console on a phone reads a context head in two calls.
- Phase 4: the console's reads are root-version + hot-prefix, never a walk.

## Open, carried

- R2 conditional-put semantics (If-None-Match on PutObject) — verify first thing in phase 3; fallback: exists-then-put with the fork tolerance covering the race.
- Pack files / cold tier for superseded versions and old transcripts — RFC-0005 names them; after v1.
- Multipart threshold and whether the distilled transcript (small) is stored beside the raw blob or only in the context store — phase 3 with the addressing decision from phase 2.
- Listing cost for a long-lived root with many hot events between compactions: compaction cadence on the S3 store (per submit? nightly?) — dogfood week decides.
