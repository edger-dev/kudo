# Spec — a worker's launch pre-answers the agent CLI's first-run prompts

**Contract.** The selected harness supplies the options and configuration that
keep an unattended worker from stopping at a prompt no one answers. Project MCP
servers are not offered, promotions and first-run tips are switched off, and
startup input is a fixed kickoff rather than a human takeover.

Claude declines servers named in every relevant `.mcp.json` in its launch
settings and keeps its existing trust behavior. Kimi uses an isolated per-lease
home, writes mode-`0600` configuration, trusts the workspace only for that
process, and enters its kickoff through the terminal's Kitty Enter encoding.
Kimi cannot trust a workspace while declining its `.kimi-code/mcp.json`; a repo
declaring project servers is therefore refused before launch in either MCP mode,
rather than loading them or leaving an unattended trust prompt.

**Chosen.** An unattended pane has no person at it; a prompt there means a
silent worker until the waker's back-off passes. Pre-answering known prompts is
cheaper than detecting and reporting a stuck pane. Explicit refusal is the only
safe behavior where a harness cannot express kudo's project-server policy.

**Rejected.** Detecting a pane stuck at a prompt and reporting it for a person:
it fixes nothing unattended. Strict MCP on every launch merely to decline
project servers: that also drops user servers needed by non-strict deployments.
Copying Kimi configuration with ordinary writable-file permissions: provider
settings can contain credentials.

**Escape hatch.** A person taking over the pane answers anything new. A future
Kimi launch mechanism that separates workspace trust from project-MCP loading
can replace the explicit refusal, with a real-CLI conformance check.
