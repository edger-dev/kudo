# Design note, 16 Oct 2026: the node daemon and the hub boundary

Baseline from the pinned code: the node is a composition root that reverse-dials the hub and registers connectors (jobs via moco-job); the shim is an MCP server on stdio inside the session, dialing the hub, workspace identity from its cwd; every node is reached through the hub and none has a local listener. Contexts add one question the crates do not answer: **where the context engine runs.**

## Decision: the context engine is a library linked into every composition root that needs it

Shim (pull, submit, head, the hook decisions), console in wasm (the phone), node (cache sync before a worker starts). Store traffic goes engine → S3 directly from whichever root holds the engine. Consequence: the Stop hook asks "next item?" with no node and no hub on the path, so a worker survives both restarting.

Rejected: a context connector on a node (a node must be awake for every pull/submit; the phone cannot enqueue at night; contradicts spec-store-reachable). In the hub (the hub routes and never owns — YJ's correction, 16 Oct).

## The boundary — three rules

1. **Bytes never cross the hub.** The hub carries node/job calls and **events** (worker started, item submitted, lease ended) that the console subscribes to for live updates instead of polling S3. It inspects nothing.
2. **A node is replaceable.** Killing it loses panes and a cache, never state; claims expire and the item is re-pulled elsewhere.
3. **The hub is replaceable.** A restart loses live subscriptions only; nodes already reconnect forever.

## Responsibilities, bounded

| Root | Owns | Never |
|---|---|---|
| hub | node registry; routing calls to connectors; event fan-out; the console's gateway | store; persist beyond liveness; interpret a payload |
| node | processes and panes; the PTY + terminal lens; the launcher (worker settings + MCP flags); the local working-memory cache and its sync; secrets for its children; liveness | decide what to pull; hold queue state; read a context's meaning |
| shim | MCP tools pull / submit / enqueue / head; the hook subcommands (same binary); cwd → mounts via the context's repos declaration | hold a secret of its own (gets S3 creds from the launcher env); talk to a node directly |
| console | a face over hub events + the engine's reads/writes | logic a second face would need |

## Decision: the phone's write path = direct S3 with a prefix-scoped token (YJ, 16 Oct)

The console holds a prefix-scoped object-store token; enqueue is a put-once from the browser; no node, no hub on the path. Rejected: through a node when awake (night enqueue waits); through the hub as a signed proxy (the hub would touch bytes).

## Plan delta

- Phase 0: no change (node on both nodes, shim reaches both — as written).
- Phase 1: the shim grows the hook subcommands and the context-engine link; S3 creds reach it via the launcher env from the node.
- Phase 3: the context engine crate carries the moco S3 backend; a scoped token for the console; hub gains the event channel (one new message kind — the only hub revision v1 needs).
- Phase 4: console = hub events (live) + engine reads/writes (direct). "Take over" = hub call to the node's pane connector.

## Open, carried

- Token scope and rotation for the phone (per-prefix, time-boxed; who mints it — the node that holds the root credential, on request through the hub, is the leaning).
- Whether events also carry the submission id so the console can fetch exactly one object instead of re-listing — leaning yes, it is an id not bytes.
- The hub README's "project coordinator" wording predates nodes+connectors; align when the hub revision bumps (no re-expression in kudo).
