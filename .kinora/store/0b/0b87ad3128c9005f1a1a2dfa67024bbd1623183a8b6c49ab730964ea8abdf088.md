# Plan — v1: the shim becomes a real hub consumer

**Task:** kino://e5b8d5926fdbaa8b237322ee11c93b731151a9f330b459499b611690a6787d23

**The blocking fact this plan is built around: there is no job connector yet.**
`moco-job` is a library; nothing on any node answers a `RoutedCall` for it. The
job surface the brief's tool list assumes therefore has nothing to reach, and the
task forbids stubbing it — a face that fakes a capability is a face holding
engine logic. So v1 builds the parts that are real today and stops cleanly at the
boundary, rather than inventing a far side.

Phases 1–2 are unblocked and shippable now. Phase 3 waits on
`moco:2510f2c0c82179acb1eddd256ae315f94fa2b95e6800f343a8c84b8a2e0dd2d4`.

**Two decisions taken up front:**

- **MCP via `rmcp`** (the official Rust SDK, currently `3.0.0-beta.2`) rather than
  a hand-rolled JSON-RPC layer. Protocol-version negotiation, tool schema shapes
  and error semantics are exactly where a hand-rolled server *mostly* works and
  then breaks against a client update. Pinning a beta is tolerable **because this
  is a face** — replaceability is the property the kind exists to guarantee
  (kino://7ea24d8f08c2e3e9c4502030a86fd9d5f9e36c1067d7e2d034d2796177e719ec).
- **`hub-protocol` as a git dependency pinned to a revision**
  (kino://8b09e3e9bdc7712b5e53412964fd2d4668e095e2a13e3d2b74c77e1bac3c11de), the
  first application of that contract.

TDD throughout; whole suite green, zero warnings.

## Phase 1 — the crate exists and dials the hub

Prove kino://121ac6ebe48b717b93e775f5a0526076a9230ec0e10e748dbcbaf181bf758120
(the stateless-proxy half).

- Create `crates/kudo-shim`, kudo's **first** crate: add to workspace `members`,
  `[lints] workspace = true`, drop `tests/architecture.rs`.
- A stdio MCP server over `rmcp`, launched as a session child.
- A `ConsumerApi` client dialed at a configured hub address; **no node-local
  path** exists by contract
  (`hub:bf406db5b660bd595cccdfcec5921121bb5a1ac9281a0d9a5c28be2d7ccc79b4`), so a
  missing hub is a clear startup error, never a silent degrade.
- One real tool: **`nodes`** — the mesh as the agent can see it, from
  `ConsumerApi::topology()`. Genuinely useful on its own ("what is reachable, and
  what can it do?"), and it needs no connector, which is why it comes first.

*Tests:* the tool lists nodes, links and connector descriptors from a topology
snapshot; an unreachable hub produces an actionable error naming the address, not
an empty list. *Status:* **done** — `crates/kudo-shim` is kudo's first crate:
`hub.rs` (the `ConsumerApi` lane), `mesh.rs` (a pure, host-tested rendering),
`error.rs`, `server.rs` (the `nodes` tool), `main.rs` (stdio). 6 tests green,
clippy clean. Commit: `d4c092b`.

Verified **against a real mesh**, not only in tests: a real hub on 127.0.0.1, a
real node serving its reference files connector, and the shim driven over actual
MCP stdio — `nodes` returned `alpha / stable / files-0 (files)`.

Three things worth carrying forward:

- `serverInfo` initially reported the SDK's name (`rmcp`) rather than the shim's.
  The agent sees that name when choosing a tool, so it needed an explicit
  `get_info`; the `server_handler` shorthand cannot express it.
- Failure and emptiness are kept distinguishable at **both** levels — a failed
  topology call is a tool *error*, and an empty mesh renders as the sentence
  "no nodes are connected to this hub". Either one rendering as blank output
  would make a down hub look like a healthy idle one.
- The hub is dialed **before** serving, so a missing hub exits with an actionable
  message instead of producing a server that looks healthy and fails every call.

## Phase 2 — routed calls, proven against a real connector

Prove kino://7c16a4ca840ff15005c5e90cca00d3d34e639ee346aadb8807863e860366118b.

- Per-request node selection: a `node` argument plus an optional `link`, built
  into a `LinkSelector`. Omitting the link takes `stable`, and the hub falls back
  to `stable` when a requested link is absent
  (`hub:08c3ce357742ccf578caddcfb6578a92216b515adcfe1ac9de4543406be52cb0`) — so a
  solo single-link setup passes no routing arguments at all.
- `RoutedCall` plumbing with a connector-defined payload codec, and errors that
  **preserve where they failed**: hub-could-not-deliver is a different answer
  from connector-refused
  (`hub:45af8b01ab1929e94682ed82013a4aad0b48af81c61b3dea89d7b8323cf94752`).
- Exercised end to end in tests against hub's reference **files** connector — a
  connector that genuinely exists. It is a *test target only* and ships no file
  tools on the agent surface; the point is to prove the routing path with
  something real rather than a mock of the far side.

*Tests:* a routed call reaches a files connector on a test node and returns its
bytes; an absent link falls back to `stable`; an unknown node fails as a hub
error and an unknown method as a node error, each distinguishable.
*Status:* **done** — `route.rs` (`Target` → `LinkSelector`, and `RouteFailure`)
plus `HubClient::route`, with `ShimError::Route` carrying the side. 9 tests
green, clippy clean. Commit: `9ae8e2d`.

Run against a **real** hub and a **real** node serving the reference files
connector, added as dev-dependencies on the same pinned revision. All three
plan tests pass, plus an unknown-*connector* case (also node-side: it reached
the node, which is what the distinction is about).

Two things worth carrying forward:

- **The message carries the boundary, not only the variant.** `failure()` is for
  code; the text is what a person or an agent reads, and it has to say whether
  the call arrived. The tests assert the message content for both sides, so a
  future refactor cannot quietly reduce them to "route failed".
- **Payloads stayed bytes end to end**, which is what makes the `facet` skew
  across components a non-event here. Phase 3 must keep that property: encode to
  bytes on each side rather than sharing a derived type.

*Deferred from this phase:* a routed call has no timeout — a connector that
never answers blocks its caller. Harmless while the only caller is a test, and
it needs deciding before a tool exposes routing to an agent.

## Phase 3 — the job tools (blocked)

Prove the rest of
kino://121ac6ebe48b717b93e775f5a0526076a9230ec0e10e748dbcbaf181bf758120 —
the tool surface and the workspace key.

**Blocked on a job connector existing in moco.** When it does:

- The tool surface mirrors the engine's Func surface minus `decide`, which stays
  off the agent's surface entirely
  (`moco:08fb4168eb094a53a5d6208430066d0f89d891073e1b24dda3ace5c81fe56db2`).
- **The shim sends its cwd; the engine resolves it to a workspace.** Resolving a
  git worktree root is the workspace definition
  (`moco:0d85bf8a00d18597ab8446e3ff9a95c7e1a25e7e0866cf33f03f4509c2f57c2f`), owned
  by the engine — a second face would need the same rule, so by
  kino://a9a94ad3464ebf50c30bffcfe64d4596384d5d122c5dfb3fb992b1aa73cd7eba it must
  not live here. The shim reports *where it is*, not *what that means*.
- A foreign-workspace write surfaces the engine's own refusal, unwidened
  (`moco:bb38e0d68b4090f86ae94c4ca44100c4afbfd41ffce285b61f50c599dd3e4cc2`).

*Status:* **done for the tool surface; the workspace half deferred.** Commit:
`fab715b`. Four tools — `job_list`, `job_start`, `job_tail`, `job_kill` — plus
`kudo-node`'s daemon binary, so there is a substrate to route to. 12 suites
green, clippy clean, driven end to end over real MCP stdio against a real hub,
a real node and real child processes.

- **cwd is the workspace key, and it works.** `job_start` defaults the working
  directory to the shim's own — the session's project directory, inherited for
  free. A job started with no `cwd` argument printed the session's directory.
- **No blocking `wait` tool, deliberately.** Phase 2 logged that a routed call
  has no timeout, and `wait` is precisely the call that would never return.
  `tail` carries status, so polling observes everything and nothing can wedge a
  lane. The Phase 2 finding is closed rather than walked into.
- **Workspace *ownership* is deferred**, because the engine does not have it:
  moco has no workspace concept at all, so there is no foreign-workspace refusal
  to surface. It arrives with
  `moco:2510f2c0c82179acb1eddd256ae315f94fa2b95e6800f343a8c84b8a2e0dd2d4`;
  inventing it here would be a face manufacturing engine semantics.

Two defects found by driving it for real, neither visible from unit tests:

- **A finished job reported `Running` forever.** Nothing reaped it, because
  every existing test happened to call `wait`. A poll-only caller — which is
  what this surface is — would have waited for news that never came. Fixed in
  the engine: `tail` now settles the job it reads. The lesson is that the
  polling surface had to be *used* to notice, since the unit tests all took the
  other path.
- **`jobs.rs` must never name `facet::Facet`.** moco's wire types derive moco's
  facet (0.43); this crate's is hub's (0.50) — different traits, same name — so
  a generic helper bounded by the local one does not compile against the
  engine's types. The version skew surfaced as a compile error exactly where it
  should, and concrete types keep the bound inside moco.

## v1 boundary — explicitly out of scope

- **The human console.** A second face is what would force shared logic down into
  the engine; until it exists, that pressure is theoretical.
- **Any file tool on the agent surface.** The files connector is a test target
  for Phase 2, nothing more.
- **Converging `facet` versions.** The shim will carry two (0.50-rc.5 via
  `hub-protocol`, and moco's 0.43.2 when Phase 3 lands). Safe only because a
  boundary carries opaque bytes; do not reach for a shared typed value.
