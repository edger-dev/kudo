# A node decides whether its workers bypass permissions

**Chosen.** A worker bypasses its agent CLI's permission prompts only when its
node says so: `KUDO_WORKER_BYPASS=1` in that node's own environment (its
kudo-node service settings). The console's start request never carries it. The
selected harness maps the choice: Claude uses `--permission-mode
bypassPermissions`; interactive Kimi uses `--auto`. Kimi print mode always uses
auto permissions, so a Kimi headless launch without the node's bypass opt-in is
refused before launch.

**What this does and does not hold.** It is the node's opt-in, not a boundary
against whoever can start jobs: on an ungoverned node a start request's env
reaches the job, so a hub caller could set the variable — but there it could
already run any command with bypass enabled. A governed node refuses env in
start requests, so there only the node's own setting counts. The boundary
against hub callers is governance.

**Why.** Whether tools may run unasked is a property of where they run: yolo is
a container whose outbound traffic goes through the OneCLI gateway, pc is not.
Kept with the node, the console never makes a worker bypass permissions on a
machine that did not agree to it. Refusing non-bypass Kimi print mode avoids
claiming an unattended mode that cannot ask.

**Rejected.** A console-side flag on the start request: it would let any caller
ask for bypass anywhere, and on a governed node env is refused anyway. Bypass
for every worker: workers on pc would run tools unasked. Inheriting a user's
Kimi `auto` default for a non-bypass worker: the per-lease configuration selects
manual mode instead.

**Escape hatch.** Unset or any other value: an interactive CLI asks as usual,
and a human answers in the taken-over pane. Kimi headless has no such escape;
use interactive mode or explicitly opt the node into bypass.
