# A node decides whether its workers bypass permissions

**Chosen.** A worker runs its agent CLI with `--permission-mode
bypassPermissions` only when the node it runs on says so: `KUDO_WORKER_BYPASS=1`
in that node's own environment (its kudo-node service settings). The console's
start request never carries it.

**What this does and does not hold.** It is the node's opt-in, not a boundary
against whoever can start jobs: on an ungoverned node a start request's env
reaches the job, so a hub caller could set the variable — but there it could
already run any command, `claude --permission-mode bypassPermissions` included.
A governed node refuses env in start requests, so there only the node's own
setting counts. The boundary against hub callers is governance.

**Why.** Whether tools may run unasked is a property of where they run: yolo is
a container whose outbound traffic goes through the OneCLI gateway, pc is not.
Kept with the node, the console never makes a worker bypass permissions on a
machine that did not agree to it.

**Rejected.** A console-side flag on the start request: it would let any caller
of the hub ask for it anywhere, and on a governed node env is refused anyway.
Bypass for every worker: workers on pc would run tools unasked.

**Escape hatch.** Unset or any other value: the CLI asks as usual, and a human
answers in the taken-over pane.
