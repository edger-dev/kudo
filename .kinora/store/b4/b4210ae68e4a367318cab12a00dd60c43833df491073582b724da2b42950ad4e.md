# Spec — a contract may be declared in one repo and realized in another

**Contract.** A spec lives with the component that **understands the
requirement**. Its implementation lives with the component that **can satisfy
it**. These need not be the same component, and when they differ the
`// implements:` citation is what binds them — nothing else does.

The worked case: `job-durability-both-kill-vectors` is a moco spec requiring a
service unit configured with `KillMode=process`. Moco ships no daemon binary; the
node daemon is packaged in hub. The spec belongs where the requirement is
understood; the unit belongs where the packaging exists; the citation crosses the
gap.

**Chosen.** Allow the split, and make the citation carry the weight. In a single
repository a contract and its code were held together by **proximity** — they
were edited in one commit and read in one directory. Split across repositories
that force is simply gone, and pretending otherwise produces contracts nobody can
satisfy and implementations nobody can trace.

**Rejected.** Requiring a spec to live wherever its implementation lives. It puts
the contract where the requirement is *not* understood — a packaging repo would
own a durability rule it has no reason to reason about — and it fragments a
coherent design across repos by accident of who happens to build the artifact.
Also rejected: duplicating the spec in both repos, which produces two texts that
drift and two answers to one question.

**Escape hatch.** When the same requirement is genuinely understood in both
places, that is a signal the boundary is wrong, not that the spec should be
copied — re-examine which component owns the capability.

The form of the cross-repo citation is specified separately, in
the cross-repo citation spec.
