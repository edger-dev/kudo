# Decision, 25 Oct 2026: search at kura scale (kura design, 2 of 3)

Designs kino://4e307377e8cffb5a701e86f96340cdbf37db43d28755f6819194c4764779345d (the object-store backend in moco).

## The gap

A root version lists every entry inline (~380 B each) and a commit rewrites
it whole: at 100k photos, ~38 MB per commit, every version kept.

## Chosen

- **Root shape:** a content-defined chunked tree (prolly), in moco —
  `moco:0c5355818d4ad254ff4e0184c89ecb486e2968dd59fc653f0324d2ab4920fa35`; every kinora root and large kinographs use it — `kinora:5ed885facf8dcd8640c31572d3de485d92d991089f0414e6d696409fbf2ae897`.
- **Queries run locally:** each device keeps a SurrealDB cache derived from
  the ledger and the root trees — rebuildable, never synced, never the source
  of truth; edits go through `kinora store`. Works offline, phone included.
- **Filters:** small styx predicates over metadata, in kinora — `kinora:3b5a71c67426049bf03366b5297dedcf24b2768060631f363203c28855a7dbf4`.
  Metadata only in v1; full text later in the local cache.
- **Backup rules:** kura evaluates the predicate on its cache and hands moco's
  working copy the keys to keep; moco stays free of metadata (amends
  RFC-0005's "Moco enforces").

## Open

- SurrealDB embedded on iOS/Android and in the browser: verify before kura's
  viewer depends on it.
- Chunk target size; the tree's migration ordering with the roots-stream
  rollout (one format change or two).
- Chunking very large files (kura design 3 of 3).
