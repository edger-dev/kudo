# Design note, 16 Oct 2026: the dogfood week and the inbox

Baseline: `inbox` is kinora's default root; a kino moves root by an `assign` event resolved at compaction (no copy); cross-root references are pinned; an existing inbox tool already delivers a kino into another repo's inbox over the hub as a *staged* store the recipient commits. kudo's config pins its inbox policy to `never` (kinora's default is MaxAge 30d) — keep `never`: friction must not age out before triage.

**Boundary refinement (corrects the 16 Oct node/hub section, rule 1):** a project ledger is git on a node, so a kino delivered to a repo's inbox is a routed call to the node holding that repo, payload uninspected. Rule 1 reads: *context-store bytes never cross the hub, and the hub never persists.* Repo-ledger deliveries are node calls, as that inbox tool already does them.

## Which inbox — by "a write goes to the store owning the root"

- Friction about a **component** → that repo's inbox; an `assign` promotes it to a task in place.
- Friction about the **way of working** (phone, night rhythm, console) → the personal context store's inbox.
- **Workers file inbox entries too** ("could not resolve kino X") — rough edges the author never sees otherwise.

## Capture

A shim tool `inbox` {line, body?}; provenance from the lease (context, session, line). From the phone: direct put to the personal inbox; a repo-inbox entry is staged until that repo's node is awake. Zero-cost capture is the point — a rough edge you must leave the pane to record goes unrecorded.

## The week as a measurement (all derivable from hook-trace kinos + inbox; the console shows it, nobody tallies)

| Measure | Why |
|---|---|
| sessions started from kudo vs bare CLI | the rule of the week; a bare session is itself a friction entry |
| items pulled / submitted, by context | the loop ran |
| lease ends by condition; takeovers | which of the four conditions fire at night |
| submissions with lines downgraded to claimed | citation enforcement bites or is gamed |
| re-pulls after deadline | the crash path was exercised |
| phone-only actions | the no-node-awake path was exercised |
| inbox entries by component, and by blocks-the-loop | the triage input |

## Decision: the week's record is a context of its own (YJ, 16 Oct)

A `kudo-dogfood` context in the personal store: its head holds the week's state (cold-readable mid-week from the phone); each day's measures land as a submission; triage is the final submission. The week is run by the thing it tests. Rejected: the inbox alone (no verdict mid-week); a daily rendered page (authored by nobody, holds no verdict — the rendered-page tier is a *view* of this context, not its record).

Work set for the week: the edger repos themselves (kudo, kinora, moco, hub, tsui as touched) and facets; nothing from the workplace side (IP boundary). Rule: every session of the week starts from the console (pick context → start worker, or take over a pane); no bare `claude` in a repo.

## Triage at week end

Each inbox entry → `assign` to tasks, or superseded with a "won't" note. Blocks-the-loop entries become the next task (as the plan says). Phase 5 done-when sharpens: *the inbox is triaged (every entry assigned or won't) and the measures are recorded as the dogfood context's final submission*; then task and plan resolve.

## Plan delta

- Phase 1: the shim's `inbox` tool (it is a store call like submit; trivial once submit exists).
- Phase 4: the console's measures view = one query over hook-trace + inbox kinos (a face feature).
- Phase 5: as above; night sessions run as ordinary workers under contexts with the budget lease-end; the morning read is the head on the phone.

## Open, carried

- Personal inbox policy after triage (MaxAge is fine once assigned entries have moved; `never` until the first triage proves the flow).
- Whether a bare-CLI session can be detected mechanically (a SessionStart hook installed globally that notices "no context bound" and files the friction itself) — nice, but it installs kudo hooks outside the launcher; decide in phase 5.
