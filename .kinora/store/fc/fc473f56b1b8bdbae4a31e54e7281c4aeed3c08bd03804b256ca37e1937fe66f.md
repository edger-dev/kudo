# Spec — a mirrored context store pulls before it reads and pushes as it writes

**Contract.** A context store may have a **mirror** (an object store, named
by `KUDO_CONTEXT_MIRROR`: `s3://bucket/prefix` with `AWS_*` credentials, or
`file:///dir`). With one, every operation **pulls** the mirror before it reads
the store, and every write is **pushed** as soon as it lands. Two machines
whose stores share a mirror therefore act as one store: an item enqueued on
one is pulled on the other, a claim taken on one is seen before the other
claims, a head superseded on one makes the other's stale submit refused.

Pulls within one process are spaced at least a second apart; a hook or tool
call is one process, so each still starts from the mirror's state. A store
with no mirror behaves exactly as before.

A claim two machines race for is decided as on one machine — the birth with
the smallest lease holds it — once both births are in the mirror; a submit
pulls first, so the losing lease's submit is refused, never silently
accepted.

**Chosen.** Sync inside the store, at read and write, rather than at session
boundaries. The pull loop's correctness rests on seeing other writers
(claims, heads), and those writers are now on other machines; syncing only
at worker start would let two machines claim one item for a whole session.
The mirror's put-if-absent push and remembered sends make a write cost only
the new files' uploads.

**Rejected.** Pull-before-start and push-at-submit only (the 16 Oct sketch):
claims and heads written mid-session would stay invisible to the other
machine until its next session. A lock in the object store (needs leases on
the lock itself; kinora's model is forks, not locks).

**Escape hatch.** A machine that is offline keeps working on its local
store; its writes push on the first operation that reaches the mirror again,
and the next pull folds the other side's writes in — conflicts surface as the
same forks and refusals as two workers on one machine.
