# Design note, 16 Oct 2026: the console — views are data, layout is a value, later a kino

## Readers and the question each view answers (decision cost: glance / skim / wall)

| Question | Tier | Source | v1 |
|---|---|---|---|
| What is running now, where? | glance | hub: nodes, workers, the context each holds | yes (phase 4 as written) |
| Where does this case stand? | skim | the context head: verdict, next action, established, open — the same block the worker reads; first three lines = the card | yes |
| How did it get there, who did what? | wall, on demand | supersedes chain of the head + submission backlinks; regroup by run **or by session** (makes "session = lease" visible: one context across sessions, one session across contexts) | yes — the **trace timeline**; the tracer bullet needs it ("find both workers' results") |
| What touched this across cases? | query | index: by repo, session, date, link type | mostly post-v1; cheap once the index exists |
| What do I do about it? | act | enqueue an item; take over a pane | yes; redirects/interventions post-v1 |

## v1 shape: three panes (chosen; YJ: "three panes for now")

Left = where (nodes, contexts, workers, live). Middle = the context head rendered as the worker sees it. Right/below = trace timeline, superseded heads and submissions interleaved newest first, each expanding to evidence / transcript, with the run-or-session regroup. Phone: middle pane only, trace as a drill. Every pane is a resolver call: head, lineage, backlinks.

Rejected for v1: graph-first (the orchestrator's round-map style) — informative only once stages exist, submissions are linear per context, layout was the costliest code in the orchestrator's console. Rendered pages + live sidebar (serve `kinora render`) — not live, loses "watch it pull"; it is the right **historical, read-only tier** later and is how daily notes become rendered views post-v1.

Lessons carried from the two earlier consoles: shell (multi-host, per-node modules, one reading pane), case page + detail pane, lineage view (→ supersedes chain). Not carried: per-page components that own their fetch (the orchestrator console's case/run/detail pages) — the reason its layout could not move; this is the "current approach" YJ is unhappy with.

## Horizons (YJ, 16 Oct)

1. **v1, Dioxus**: fixed three panes, but built under the four rules below so the arrangement is a value, not code.
2. **Mid-term, tsui shell**: a customizable shell; the user owns layout (RFC-0002: splits, multiplexed views of the same data, universal text). The v1 arrangement value becomes tsui's layout document; the v1 renderers become tsui view providers.
3. **Long-term, adaptable + DSL**: **a layout is a kino** — its own kind, stored, superseded, shared across devices, writable by an agent as easily as by a human (tsui's "UI is a projection of data" and kinora's "a kinograph is take-these-kinos-arrange-render" are the same shape). "Adaptable" = the layout kino is itself selected by a query (e.g. a context in a waiting state opens a different head than one in flight). DSL host: styx is the natural candidate since kinora config and the ledger already use it — not decided.

## The four rules v1 must obey (so horizons 2–3 replace a data structure, not a codebase)

1. A pane is `render(kind, resolve(query))` and nothing else; no pane fetches its own data from the hub.
2. The arrangement of panes is one data structure (a struct literal in v1), read from one place — never component nesting.
3. Renderers are keyed by kino kind (context head, submission, transcript, node, worker); a second renderer for the same kind is allowed (tsui's same-blob-two-views, later).
4. Selection (current context, current submission) is one state value, not component props.

## Plan delta

- Phase 4 done-when gains: *a second arrangement of the same panes is produced by changing the layout value only* — the cheapest proof the console is a face, and the test the tsui shell must pass anyway.
- Phase 4 scope gains the trace timeline with the run/session regroup; everything else as written.
