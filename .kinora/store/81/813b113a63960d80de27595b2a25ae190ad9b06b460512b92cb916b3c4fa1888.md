# Spec — Kudo MCP exposes live session messaging

**Contract.** Every `kudo-shim` MCP server with a hub address joins one live
logical session through the hub. A worker uses its lease as the session id. A
bare session uses `KUDO_SESSION_ID` when its launcher supplies one, or a
generated UUID otherwise. Multiple shim processes with the same id are one
agent session, not independent targets. Registration carries local node,
harness, current workspace, and optional worker context. Workers register in a
background retry loop without blocking startup. A reconnect registers the same
session and mailbox again.

The MCP offers `session_list`, `session_send`, and `session_messages` whenever a
hub is configured. Listing returns local and one-hop peer sessions with qualified
ids and one entry per logical session. Sending takes a target and body, generates
or reuses a message id, and returns `delivered <id>` only after the receiving
shim accepts it. Unknown, offline, or refusing targets return errors. Retrieval
drains the current session's pending messages without promising ordering across
concurrent publishers.

A transport failure or timeout refreshes the connection and registration without
replaying an ambiguous send; the original error is returned after a bounded,
best-effort refresh. The caller retries explicitly with the same id. Receivers
retain only an id/content fingerprint after draining, making an identical retry
idempotent and refusing changed content under that id. File-backed delivery and
retrieval are serialized by a crash-released per-session lock.

**Local delivery.** Every session writes each accepted message to its
file-backed local mailbox before acknowledging. All shim and hook processes
sharing a session id share that mailbox, so any MCP process belonging to the
agent can drain a message accepted through another registration. A worker's
Stop hook drains pending messages at a turn boundary and injects their sender,
id, body, and reply address as the next prompt. An open claim and an ended lease
retain their existing priority. Message delivery clears idle waiting without
consuming a queue item. Bare sessions use `session_messages`; no terminal text
is injected implicitly.

**Scope.** The hub retains no offline queue or history. A local mailbox holds
only messages accepted while the session was live, until drained or deleted. No
automatic terminal input, multi-hop forwarding, or sender-supplied identity
override is offered. `KUDO_SESSION_ID` is trusted launcher configuration, not a
message argument.

**Why.** Agents need to discover and coordinate with live work on connected nodes
while preserving Kudo's worker claim/turn invariants and portable MCP behavior.
Harnesses may run several MCP clients for one agent; identity and delivery must
not fragment across those implementation details.

**Escape hatch.** A harness-specific immediate delivery adapter or a singleton
session broker can be added without changing message routing, stable identity,
or acknowledgement.
