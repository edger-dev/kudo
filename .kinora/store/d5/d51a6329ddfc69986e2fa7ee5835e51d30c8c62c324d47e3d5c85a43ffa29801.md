# Spec — component dependencies form a DAG with no upward edges

**Contract.** The Kudo component set is a **strict dependency DAG**. A component
may depend downward, never upward and never cyclically:

```
hub-protocol   — pure message and identity types; depends on nothing else here
     ↑                        ↑
   hub                      moco          — binds the published protocol so it is
 (transport)              (engine)          reachable; never hub's internals
                             ↑
                    kinora  ·  kura
                             ↑
                    kudo  ·  tsui
```

Two edges must **never** appear:

- **transport → engine.** The hub must not depend on moco, or know what a job,
  a rule-set, an approval, or an audit record is.
- **engine → face.** No engine may depend on a consumer that presents it.

**Chosen.** A DAG fixed across the whole component set, not per pair. This
generalizes the layering already established for the storage stack (Moco ←
Kinora ← Kura), whose value was dissolving a would-be dependency loop before it
formed rather than breaking one afterwards.

**Rejected.** Case-by-case dependency decisions. Each looks locally reasonable,
and a cycle is only visible from outside any one repo — which is exactly the view
no component has. Also rejected: allowing the transport to depend on an engine
"just for types"; a shared vocabulary between them is the first step to the hub
needing a rebuild whenever a capability changes.

**Escape hatch.** A capability that genuinely needs the transport to act on its
semantics earns a first-class protocol method, agreed at the transport's
boundary — it does not get there by having the transport import the engine.

This spec states *which* dependencies are legal. It does not decide **where a
given file belongs** when several placements are legal; that is the component's
*kind*, specified separately.
