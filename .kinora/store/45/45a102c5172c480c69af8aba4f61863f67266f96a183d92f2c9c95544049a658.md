# Spec — a cross-repo reference cites the stable id, not the name

**Contract.** A `// implements:` reference to a spec in **another** component's
ledger cites that spec's **stable identity hash**, qualified by the owning
component:

```
// implements: moco:a8f6cfd51b1c823d4f9331e01962f7c2b88976587cff32120f3ce98a803c24c7
```

- The **id is authoritative** and is what any tool resolves.
- The **component prefix is a locator**, not part of identity — ids are
  content-addressed and globally unique; the prefix says which ledger to look in.
- A trailing `(spec-name)` is permitted for readability and is **never
  authoritative**: nothing resolves against it, and it may drift without breaking
  the link.

A reference **within** the same repo continues to cite the name unqualified
(`// implements: argv-not-shell`).

**Chosen.** Id across repos, name within one — a deliberate asymmetry with a
reason. Inside a repo, a rename and every citation of it are fixed **atomically
in one commit**, so a name is safe and far more readable. Across repos no such
commit exists: the citing repo may be at any revision, or not checked out at all,
so a rename would break the link **silently** and stay broken until someone
happened to try resolving it. Only the identity hash — which survives renames and
re-versions by construction — can hold a link nobody is in a position to update.

**Rejected.** Names across repos: readable, and wrong in exactly the case the
reference exists for. Ids everywhere including in-repo: pays a real readability
cost against a rename risk that is already atomic there. Abbreviated ids: git can
disambiguate a short hash against one object store, but there is no single index
across ledgers to disambiguate against.

**Escape hatch.** A version qualifier (`…@<version>`) may be appended when code
depends on a *specific version's* behavior rather than the durable contract.
Current practice in the component repos omits it, citing the identity alone.
