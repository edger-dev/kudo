# Spec — the context store is reachable with no node online

**Contract.** The kinora store that holds contexts is backed by an
**object store** (S3-compatible, hosted) rather than by a git clone on one
machine. A worker on any node, and the console from any device, reads and
writes the same store, and none of them needs another node to be awake to do
so. Objects are content-addressed and write-once, as kinora already defines
them; the backend changes where the bytes live, not what a kino is.

The requirement is declared here, in the composition root that needs it; the
backend is realized in kinora, the engine that owns the store. The citation
binds them, as the cross-repo contract rule allows.

**Chosen.** A hosted object store, inside the first eight weeks. The daily
loop this plan targets runs from a laptop that sleeps, a container host that
is sometimes off, and a phone; a git-backed store reachable through whichever
node happens to hold it is exactly the liveness coupling the materialize pass
in the earlier prototype had to work around. Paying for the backend early
means the tracer bullet is exercised against the real topology, not a
single-node stand-in that would hide the sync problems.

**Rejected.** Git as the only persistence, synced between nodes: it ties
reads to a node being online and makes the phone a second-class client. Also
rejected: a database as the source of truth — kinora's principle is markdown
on durable storage as the disk and a database as working memory; an object
store keeps that, a database would invert it.

**Escape hatch.** Git stays the backend for a project's own `.kinora/` ledger
(specs, tasks, plans travel with the code). Only the **context** store moves;
a context may cite kinos in a project ledger by qualified id.
