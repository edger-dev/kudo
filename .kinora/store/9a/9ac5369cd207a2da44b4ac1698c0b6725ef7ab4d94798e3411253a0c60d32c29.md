# Spec — the console is a Dioxus face over the hub, and tsui is not on its path

**Contract.** kudo's human surface is a **Dioxus fullstack** app: a browser
UI (Rust/wasm) served by a native **console server** that links the context
engine (with its mirror) and the hub client, the UI calling it through server
functions. Through it a person discovers nodes, lists contexts, shows a
context's workers, head and trace, enqueues items, starts a worker on a node,
and takes one over. It stays live on the hub's event channel. It is a **face**
in the sense of the component-kind rule — presentation only; anything a second
face would need moves down into an engine, and the server functions are thin
calls into the engine and the hub, nothing more.

(Revised 21 Oct, author's decision: the browser does not read the object
store itself. The context store is kinora files and kinora's reader is
filesystem-bound; a native server links the engine as every other root does.
The phone works whenever the server's machine is awake.)

It is **rewritten** from the shell patterns two earlier Dioxus consoles proved
(multi-host, per-node capability modules, a shared reading pane, a live
transcript view). Nothing is ported; the patterns are, with their lessons.

**Chosen.** Dioxus directly, now. Two consoles of this shape exist and work,
and the toolchain (`dx`, cargo, clippy) gives both humans and agents a tight
feedback loop. The first working kudo is measured by what a person can do from
this surface in eight weeks; the surface cannot wait on a framework.

**Rejected.** Building tsui first and making the console its first app. tsui
is the right long-term home for data-driven views, but it has no code today,
and making it a prerequisite would spend the whole budget on the framework and
none on the tracer bullet. Also rejected: a TypeScript front end — weaker
feedback loops for agents, and a second toolchain to keep alive.

**Escape hatch.** A phone that must read while every machine sleeps reads the
mirror directly — a browser-side store reader with a prefix-scoped token, as
the 16 Oct note planned — behind the same server-function interface. When tsui exists, the console's generic views (lists, trees,
detail panes) migrate to it view by view; the Dioxus shell stays until the last
custom view is gone, and may stay as the wasm backend tsui renders through.
