# Spec — the loop's events are published as they are traced

**Contract.** Every loop event a lease traces (lease start, handoff, pull,
refused stop, release, submit, lease end) is also **published on the hub's
event channel**, and so is an item enqueued under a context. The topic is
`kudo/context/<context id>/<lease>/<event>` (`.../enqueue/enqueued` for an
enqueue, which no lease makes), so a reader follows one context, one lease, or
all of kudo by prefix. The payload is the event as one line — the same text
the trace kino holds — and never more: it says *that* something happened, the
store says *what*.

Publishing is **best effort**: a hook or tool publishes after the write it
reports has landed, gives the hub half a second, and goes on without it. No
hub configured, a hub that is down, a publish refused — none of them fails the
loop.

**Chosen.** Publish beside the trace, from the same call. The trace already
names every loop event at the one place it happens; publishing there means a
console sees exactly what the trace will show, with no second list of events
to keep in step. A pointer, not a copy: the hub never carries a head or a log,
so nothing on the channel can disagree with the store.

**Rejected.** Polling the store from the console (latency, and work for nobody
when nothing moves). Publishing the written kinos themselves (the hub would
carry content; a second copy that can drift). Making the loop wait for the hub
(a hub restart would stall every worker).

**Escape hatch.** A reader that missed events — it connected late, the hub
restarted, it fell behind and was dropped — re-reads the trace from the store;
the channel is a nudge, never the record.
