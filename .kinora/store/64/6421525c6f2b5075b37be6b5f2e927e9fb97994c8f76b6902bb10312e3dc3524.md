# Design note, 16 Oct 2026: context store layering

## Layers, bottom to top — links point down only; a lower layer never knows the layers above it (same rule as moco ← kinora ← kura)

| Layer | Backed by | Roots | Travels with | Knows about |
|---|---|---|---|---|
| project ledger, one per repo | git, the existing `.kinora/` | specs, tasks, inbox, rules | the code | nothing above |
| team store (later) | S3, shared tenancy | contexts, submissions, checks | the team | project ledgers |
| personal context store | S3, own tenancy | contexts, submissions, sessions, checks, watches, memory | the person | project ledgers, team store |
| working memory, per node | local moco dir + index | cache of whatever is mounted | nobody; rebuildable | all mounted stores |

## Rules

1. **Content ids are global, identities are per store.** A kino id is a hash of bytes → the same id is the same kino in any store; the union across layers cannot conflict. A head ("what nothing supersedes") is a property of one ledger. A plain id resolves by searching the mounted stack in order; a head/lineage query names the store → qualified form `<store>:<id>` (answers RFC-0006 open Q1).
2. **A write goes to the store that owns the root.** A spec filed under a context lands in that repo's ledger; the submission links to it by qualified id. Nothing personal lands in a repo; nothing project-shaped lands in the context store. The context's "repos it spans" declaration doubles as the mounts table (naming a repo names its ledger).
3. **Index per store, merged at query time.** "Which contexts cite this spec" is answered by the context store's index only; project ledgers stay ignorant of who cites them → repos stay free of personal data by construction.
4. **Concurrency is forks, not locks.** One file per event; put-once via conditional write on S3 (If-None-Match). Two workers superseding one head at once = a fork = multiple heads (the resolver already represents this); the console shows it; the next submission merges by superseding both parents.

## Decision: a cross-store citation is **cite-and-cache** (YJ, 16 Oct)

The weak link is recorded AND the cited kino's bytes are copied into the citing store, provenance naming the origin store; identity stays at the origin. Hence the context store is self-contained for reading: the phone and a node with no repo clone read everything a context cites, and an inbox kino the repo GCs (MaxAge 30d) stays readable from the context that cited it. Cost: duplicated markdown, small under content addressing. Transcript blobs stay in moco by hash, not copied (moco's replication policy decides). This is what makes "bring your context" literally true.

Rejected: pure reference (needs the origin mounted; phone cannot read; GC dangles). Strong pin across stores (the lower layer would know the upper; cross-store GC coordination).

## Sync between node working memory and S3

Pull the mounted stores before a worker starts; push at every submit (the earlier prototype's ctx pull/push, now a store-level operation, no separate registry). The phone reads S3 through the hub/console directly, never a node's cache.

## Plan delta

- Phase 2: the context kino's repo declaration carries each repo's ledger (the mounts table); the submit tool performs cite-and-cache for every cross-store link.
- Phase 3: layered resolver (stack search for ids, store-named heads), per-store index merged at query, conditional put-once on the S3 backend, pull-before-start / push-at-submit.
- Team store and the encrypted root: post-v1, same shape as the personal store.

## Open, carried

- Store naming in the qualified form: repo-url-derived short name (as `render` already derives cache paths) vs a declared alias in the mounts table — phase 3.
- Whether cite-and-cache copies transitively (a cited spec's own in-content links) or one hop only — leaning one hop; phase 2 against real contexts.
- Fork merge UX in the console: automatic when both parents are submissions of the same item, else shown for a human — phase 4.
