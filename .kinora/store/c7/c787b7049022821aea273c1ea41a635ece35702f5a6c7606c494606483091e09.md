# Plan — v1: the first working kudo in six phases

**Task:** kino://4aef99814b668f7cbb8900eee43e35b67fdb6dbcd18ba196858f6226874cc0e2

Six phases over six weeks, two weeks of slack, starting 16 Oct 2026. Every
phase is cut so one night session can finish a step and leave the ledger
committed (`kinora store` → `kinora commit` on main → `git commit`), because
the next session starts cold and may be driven from a phone. A phase that
needs two sessions still ends each one that way.

The design notes of 15–16 Oct (inbox, `note-*`) refine every phase below with a
"Plan delta" list; fold a note's deltas in when its phase opens.

The order is tracer-bullet first: nothing is built that the end-to-end path
does not exercise, and the console lands early enough that each later phase
is reviewed by watching it, not by reading diffs.

## Phase 0 — ground (week 1, part)

- Confirm the workspace builds against the pinned hub/moco revisions (done
  15 Oct: `cargo check --workspace` green).
- **One host for now** (decided 20 Oct): an incus host (pc or edger) runs the
  hub on its bridge, `10.100.0.1:15400`; `kudo-node` runs as a lingering
  user service on the host and in its `yolo` container, both dialing that hub;
  `kudo-shim` reaches both. Hubs on different hosts are not linked — that

- Deployed through Nix: `nixosModules.hub` (hub repo), `homeModules.kudo-node`
  (this repo), wired in the dotfiles flake for pc, edger and yolo.
- A `worker` crate skeleton and a `context` crate skeleton, empty but wired
  (done 20 Oct: `kudo-worker`, `kudo-context`, linked by node and shim).

Status: done 20 Oct — on pc: the hub on the bridge, `kudo-node` on pc and in

## Phase 1 — a worker pulls (week 1–2)

The loop is decided: kino://b9ef8909cadf0092e9b9d01eb3fc3edbe9db4f2af17f80753571d9434628b1af (from the 16 Oct pull-worker-loop
note). This phase builds it against the real CLI.

- The shim gains MCP tools `context_read`, `pull`, `submit` and `inbox`,
  plus hook subcommands in the same binary. Dry-run first, as the earlier pull
  tools were.
- `kudo-node` starts a worker as the interactive agent CLI in a terminal pane
  (the job substrate's terminal lens), under a context id and a repo path from
  the context's declaration, passing the worker settings file and the MCP
  config on the command line.
- SessionStart binds and injects the head; Stop hands over the next item of the
  same context, or lets the session end on one of the four lease-end
  conditions; the open-claim guard refuses a stop without a submit.
- Claims are write-once kinos with a deadline; an expired claim is re-pulled as
  attempt N+1.
- Observe: the node tails the CLI's transcript and relays it as events; the hook
  events (pull, submit, takeover, lease end, compaction) are the loop's own
  trace. A submission is a write to the context, never a parsed transcript.
- Done when: two consecutive items of one context are worked as two turns of
  one session; each of the four lease-end conditions ends a session once; a
  killed worker's item is re-pulled after its deadline.
- Open: claim deadline length and whether a worker may extend its own claim
  (heartbeat from PostToolUse); budget accounting from the hook's usage fields
  or from turn counts.

## Phase 2 — the context kino (week 2–3)

- The `context` kino shape: resume block (where / next / established / open),
  log, repos, queue. Submissions rewrite the block and append the log.
- Queue items are kinos too, write-once, with a state that moves by append.
- A context names repos per node; starting a worker in a repo under a
  context is one call that resolves node + path from the declaration.
- Done when: two workers in two repos on one node submit into one context.
