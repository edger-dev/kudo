# Spec — Kudo dials WebSocket hubs with optional Cloudflare Access credentials

**Contract.** `KUDO_HUB_ADDR` accepts `ws://` and `wss://` URLs in addition to
bare and `tcp://` addresses. Kudo opens a Vox WebSocket link, opens
`ConsumerApi`, and performs the existing `HUB_AUTH_TOKEN` authentication before
serving calls. Re-dials use the same URL and credentials.

When `CF_ACCESS_CLIENT_ID` and `CF_ACCESS_CLIENT_SECRET` are set, Kudo adds
`CF-Access-Client-Id` and `CF-Access-Client-Secret` to the WebSocket handshake.
They must be configured together and are never logged. With neither set, the
handshake has no Cloudflare service-token headers. These headers supplement,
never replace, `HUB_AUTH_TOKEN`.

**Why.** Native WSS lets an Incus-hosted agent use an existing Cloudflare
hostname without running a local TCP forwarder. Service tokens support an
Access-protected hostname without interactive browser login.

**Rejected.** Removing TCP support, treating Cloudflare Access as a substitute
for Vox authentication, and silently accepting a half-configured service token.

**Escape hatch.** Other WebSocket proxies work with the same URL. A future Vox
API for custom handshake headers can replace Kudo's local request construction.
