# A node decides whether its workers see only kudo's MCP server

**Chosen.** A worker is restricted to kudo's MCP server only when its node says
so: `KUDO_WORKER_STRICT_MCP=1` in that node's own environment (its kudo-node
service settings). The console's start request never carries it. Claude adds
`--strict-mcp-config`. Kimi writes an isolated per-lease `mcp.json` containing
only kudo. Unset or any other value: the worker gets kudo alongside the user's
own servers; Kimi merges those servers into its isolated config while replacing
only the `kudo` entry.

Project servers are never silently enabled by this choice. Claude declines them
in launch settings. Kimi refuses a repo with `.kimi-code/mcp.json` servers before
launch, because its current workspace-trust decision cannot be separated from
project-MCP loading.

**Why.** Which MCP servers a worker needs depends on where it runs. On the
home-lab yolos, the user's servers add first-run prompts and nothing a check
needs. Other deployments' checks read the user's own servers, and strict mode
would drop all of them. The default is off because dropping servers silently is
the worse surprise.

**Rejected.** Strict always or strict by default: it breaks deployments whose
checks use the user's tools. A per-node allowlist of server names: more control,
but a list to maintain with no current need. Merely hiding project tools from
the model while connecting their servers: that is not strict MCP.

**Escape hatch.** The user's own CLI configuration decides which servers load
when strict mode is off; a node that wants only some trims that configuration.
A future Kimi mechanism that excludes project servers without a trust prompt can
replace the explicit project-server refusal.
