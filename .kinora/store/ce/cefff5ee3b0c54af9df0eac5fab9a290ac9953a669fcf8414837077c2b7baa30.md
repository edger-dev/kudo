# Decision, 25 Oct 2026: very large files (kura design, 3 of 3)

Designs kino://4e307377e8cffb5a701e86f96340cdbf37db43d28755f6819194c4764779345d (the object-store backend in moco).

## Chosen

- **Shape:** one object per file, keyed by its whole-file BLAKE3 hash; parts
  exist only in transport. Above 16 MiB, a BLAKE3 outboard beside it, derived
  and kept with its object, so any range verifies against the file's hash.
- **Resume:** the working copy saves the multipart upload id and finished
  parts locally; a restarted put sends only what the remote lacks.
- **Hash first stays:** a large file is read twice (hash + outboard, then put).
- Specs in moco's ledger: `moco:9c0820e21030c6c665c4299894b002680e477056b4e6b9e5efe55eaeacf2b861` (a large object is one object, with a
  derived outboard) and `moco:232353ddb44c322224a58ab08e8be82862cf0779f38cbbdc01a416ceb9ceb7ea` (an interrupted large put resumes).

## Rejected

Fixed chunks plus a manifest; content-defined chunks; local-only outboards;
outboards for every object; hashing while uploading to a temp key.

## Open

- The outboard's key form (a key names its own content hash today).
- The tree group size (16 KiB assumed); how long an unfinished upload lives.

Closes the chunking item left open by kura designs 1 and 2.
