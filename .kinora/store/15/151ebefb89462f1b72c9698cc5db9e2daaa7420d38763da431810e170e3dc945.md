# Decision — remote inbox notes use authenticated online delivery

Decided by the author on 2026-11-23 after considering a dedicated object-store
mirror and direct hub delivery. This decision records the **C-lite** variant.

## Chosen

- The sending session gets one MCP tool, roughly
  `send_note(target, title, body, attestation)`.
- Delivery is direct: **MCP → authenticated hub → home receiver**. The console
  is not an entry point, and no unauthenticated public endpoint is added.
- v1 is **online only**. A successful call returns **delivered**; a refusal
  returns **refused** with the reason; an unreachable hub or receiver returns
  **unavailable** and accepts nothing. There is no queue or waiting state. The
  sender retries later. This explicitly replaces the original requirement that
  a note sent during a home outage arrives automatically later.
- Targets are short aliases such as `kudo` and `kinora`, resolved to local
  repositories in the receiver's configuration.
- The receiver deduplicates each accepted note and writes one kino into the
  target's inbox root with author, machine alias, session id, creation time,
  and receipt time. Arrivals default to unreviewed and can be listed by time.
- The receiver uses a dedicated checkout of `main`. With Kinora's current Git
  backend it runs `kinora store --root inbox`, `kinora commit`, and a local
  `git commit`. Notes are not pushed to GitHub.
- Notes are text-only with a finite size limit. **The exact limit is open**:
  16 KiB is probably too small, so implementation should examine real note
  sizes and evaluate a larger bound rather than adopting 16 KiB blindly.
- Before upload, the sending agent attests that the note contains no code and
  no employer-specific information. The tool also enforces text shape and
  rejects code blocks and configured sensitive markers. A receiver-side check
  may supplement this, but the sending-side check remains primary.
- Hub payloads stay opaque. Kudo owns only a thin, replaceable receiver;
  Kinora can take over cross-Kinora communication later.

## Backend boundary

The local Git commit is required only by Kinora's **current Git backend**, not
by the communication contract. If Kinora later moves off Git, the receiver
will use that backend's corresponding durable commit/publish operation. The
note channel itself must not depend permanently on Git.

## Rejected

- A dedicated R2 intake mirror: it provides durable offline delivery and
  existing authenticated storage, but the author prefers direct MCP delivery
  after comparing the additional receiver topology.
- Full direct delivery with an offline outbox: automatic retry and deduplication
  add roughly the same difficult infrastructure again. Deferred rather than
  silently dropped from the status model.
- A 16 KiB fixed limit: likely too restrictive for design notes like this one.

## Open

- The finite text-size limit, based on real note sizes and transport limits.
- The concrete hub authentication and credential mechanism.
- Semantic screening is best-effort: attestation and deterministic checks
  cannot prove the absence of all employer-specific information.
