# Spec — a timed-out call is not a cancelled one, and must not read like one

**Contract.** Every call the shim makes to the mesh is bounded by a timeout. When
that timeout fires, the shim gives up **waiting**; it does not stop the work.
The far side may still be running, may still finish, and may still have had every
effect the call asked for.

The error therefore says so, and names how to find out:

> the call to node 'x' did not answer within Ns. **This is a timeout, not a
> cancellation — the work may still be running.** Use `job_list` to see what is
> there before starting it again.

A timeout must never be reported as a failure to act. Silently retrying one, or
rendering it the way a refusal is rendered, are both forbidden: a caller that
reads "it failed" and starts the work again has now started it twice.

**Chosen.** Bound the wait, and be explicit that bounding the wait is all it
does. A shim that blocks forever on a silent connector wedges the agent for the
session; a shim that times out and *implies* nothing happened causes duplicate
work — the second is worse, because it is silent and the caller acts on it.

**Rejected.** No timeout at all: one unanswering connector holds a caller
indefinitely, and there is no other channel to notice through. Also rejected:
timing out and cancelling the far side — the transport has no cancellation
primitive, and inventing one that "usually" works would make the honest report
above a lie. Also rejected: an automatic retry, which is exactly how a
non-idempotent call (`job_start`) runs twice.

**Escape hatch.** The bound is configurable, so a caller who genuinely expects a
long answer raises it rather than being forced into a retry loop that would
duplicate work.
