# Note — a channel that sends a note from another machine into a Kinora inbox

Drafted by the agent on 2026-11-23 from a chat with YJ in his personal notes
folder. The goals and constraints are YJ's; the recommendation and the open
questions are the agent's. The agent read kudo's README, AGENTS.md, the console
and mirror docs, and hub's README. It did not read the code, the RFCs or the
spec kinos, so statements about current behaviour had to be checked at home.

## Why

Feedback on kudo or kinora written away from the home machines now travels by
chat message, then mail, then a manual kinora store. YJ wants it hands-free: in
any agent session he says "send this to kudo's inbox", and it arrives at home
as a kino in that repo's inbox root. The index work on kinora will happen at
home, and this channel is what keeps that loop short.

## What the first version should do

- One tool for the sending session. An MCP tool, roughly
  `send_note(target, title, body)`.
- One kino per note at the receiving end, in the target repo's inbox root,
  with provenance: who wrote it, from which machine and session, and when.
- Text only. Thoughts cross, code does not. No attachments, and a size limit.
- A check on the sending side before the note leaves: refuse code and anything
  specific to an employer. A second check may run at the receiving end before
  storing, but the sending-side check is the one that counts, because by the
  second one the content has already crossed.
- Nothing is dropped silently. If the receiver can't be reached, the note waits
  and goes later. The sender is told whether the note was delivered, is
  waiting, or was refused and why.
- Auth before reach. Nothing new becomes publicly reachable without auth. The
  console has no login, so it is not the entry point.
- Arrivals are marked unreviewed, and "what arrived since yesterday" is easy
  to list.

## Open questions in the original note

1. Transport: the existing context-store mirror, hub once it has auth, or
   straight to kudo after auth exists. The drafting agent suggested the mirror.
2. Who owns the receiver: keep kudo's part thin so kinora can replace it.
3. Naming the target: a repo name or a hub-qualified name.
4. Whether the receiver stages only or also compacts and commits.
5. The reverse direction was left out of the first version.

## Original done-when

From a session on another machine, one tool call puts a text note into kudo's
inbox root at home, with provenance. A refused note says why. A note sent while
home is unreachable arrives later. Nothing new is reachable from the public
internet without auth.
