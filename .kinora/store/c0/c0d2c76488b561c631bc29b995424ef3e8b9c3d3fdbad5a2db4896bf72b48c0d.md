# Plan — v1: the first working kudo in six phases

**Task:** kino://4aef99814b668f7cbb8900eee43e35b67fdb6dbcd18ba196858f6226874cc0e2

Six phases over six weeks, two weeks of slack, starting 16 Oct 2026. Every
phase is cut so one night session can finish a step and leave the ledger
committed (`kinora store` → `kinora commit` on main → `git commit`), because
the next session starts cold and may be driven from a phone. A phase that
needs two sessions still ends each one that way.

The design notes of 15–16 Oct (inbox, `note-*`) refine every phase below with a
"Plan delta" list; fold a note's deltas in when its phase opens.

The order is tracer-bullet first: nothing is built that the end-to-end path
does not exercise, and the console lands early enough that each later phase
is reviewed by watching it, not by reading diffs.

## Phase 1 — a worker pulls (week 1–2)

- Define the pull surface on the shim: `context_next`, `context_submit`,
  plus `context_read` for the resume block. Dry-run first, as the earlier
  pull tools were.
- A worker is the interactive agent CLI started by `kudo-node` in a terminal
  pane (the job substrate's terminal lens), under a context id and a repo
  path from the context's declaration.
- The pull loop through the CLI's own hooks: session-start reads the context;
  the stop hook asks for the next item and hands it over, or lets the session
  end when the queue is empty. Decide here which of the two is primary.
- Observe: the CLI's transcript is tailed by the node and relayed as events;
  a submission is a write to the context, never a parsed transcript.
- Done when: one worker, one node, one context in a local kinora store, pulls
  two queued items and the resume block shows both.

## Phase 2 — the context kino (week 2–3)

- The `context` kino shape: resume block (where / next / established / open),
  log, repos, queue. Submissions rewrite the block and append the log.
- Queue items are kinos too, write-once, with a state that moves by append.
- A context names repos per node; starting a worker in a repo under a
  context is one call that resolves node + path from the declaration.
- Done when: two workers in two repos on one node submit into one context.

## Phase 3 — the store moves to the object store (week 3–4)

- In **kinora**: an S3-compatible backend for a store, content-addressed and
  write-once, cited from the reachability spec here. Its task lives in the
  kinora ledger: KINORA_TASK (filed when the phase opens).
- kudo points the context store at it; project `.kinora/` ledgers stay on git.
- Done when: the phase-2 scenario runs with the laptop node asleep for one
  of the two workers, and the console (phase 4) later reads it from a phone.

## Phase 4 — the console (week 4–5)

- Shell patterns rewritten from the two earlier consoles: multi-host, per-node
  modules, one shared reading pane. No code ported.
- Done when: the tracer bullet runs from the console on two nodes.
