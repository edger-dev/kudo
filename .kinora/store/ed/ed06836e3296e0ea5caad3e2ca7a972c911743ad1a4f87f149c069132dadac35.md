# Spec — the console's arrangement is a value, and a pane is a kind rendered from a query

**Contract.** The console shows **panes**, and everything about which panes
appear where is **one value** — a layout, read from one place — never the
nesting of components. A pane is exactly `render(kind, resolve(query))`:

1. a pane never fetches its own data; the shell resolves each pane's query
   (through the console server) and hands the pane what came back;
2. the arrangement is one data structure (a struct literal in v1);
3. renderers are keyed by **kind** — node, context, worker, head, trace
   entry — and a kind may have more than one renderer;
4. what is selected (the current context, the current submission) is **one
   state value**, not props threaded through components.

v1's layout is three panes — *where* (nodes, contexts, workers), the selected
context's **head** as a worker sees it, and its **trace** timeline — and a
second arrangement of the same panes is produced by changing the layout value
alone.

**Chosen.** Layout as data, from the first version. The orchestrator's
console could not move its layout because each page owned its fetches; the
next horizons (a user-owned tsui shell, a layout stored as a kino) replace a
data structure only if v1 already is one. Proving a second arrangement by
changing the value is the cheapest evidence the console is a face.

**Rejected.** Pages that own their data (the layout freezes). Graph-first
views (informative only once stages exist). Serving `kinora render` as the
console (not live).

**Escape hatch.** A pane that needs a bespoke interaction keeps it inside its
renderer; the arrangement still only places it.
