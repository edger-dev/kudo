# Spec — a crate dependency across components is a git dep pinned to a revision

**Contract.** When a crate in one component depends on a crate in another, it is
declared as a **git dependency pinned to an explicit revision**:

```toml
hub-protocol = { git = "https://github.com/edger-dev/hub", rev = "<sha>" }
```

- **Never a path dependency.**
- Local iteration across two components uses a `[patch."<git-url>"]` override
  pointing at a local checkout. That override is **not committed**, so the
  committed manifest always describes the reproducible build.
- Moving to a published crates.io version later is a manifest edit. The pinned
  rev is the interim position, not a permanent stance.

**Chosen.** Pinned git, because it is reproducible from **any** clone regardless
of directory layout — and layout is already not uniform: the components exist in
more than one checkout tree, plus git worktrees, so "the sibling directory" names
different code depending on where you stand. A pinned revision also makes
adopting a new version of another component a **deliberate, reviewed commit in
the consumer**, which is the right friction for a boundary every other component
binds.

**Rejected.** A path dependency: the fastest loop, but it hard-codes a sibling
layout that is already untrue across checkouts and CI, and it pins no version at
all — two clones can silently build against different code with no record of
which. Publishing to crates.io: correct eventually, premature now, since the
protocol crate is `0.0.0` on pre-release dependencies and moved through five
milestones in a week; every change would force a republish before any consumer
could build.

**Escape hatch.** `[patch]` against a local checkout gives the fast cross-repo
loop while developing, and stays out of the committed manifest so that what
everyone else builds is the pinned revision.

**A constraint this does not solve.** Components are on divergent versions of
shared crates — `facet` at 0.43.2, 0.46.0 and 0.50.0-rc.5; `facet-styx` at 1.0.1
and 3.0.2. Depending on two components therefore pulls two versions of the same
framework into one build graph. That compiles, and it is safe **only** because a
component boundary carries **opaque bytes rather than typed values**
(`hub:d78fb95fddc31aa42bc927da1eaed44292529b3671d1ef9ef58ec8cd0858e51c`).
Components exchange bytes; they must not exchange `Facet`-derived types across a
boundary until the versions converge. Convergence is separate work, deliberately
deferred.
