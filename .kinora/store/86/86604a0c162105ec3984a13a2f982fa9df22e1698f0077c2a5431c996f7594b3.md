# Design note, 15 Oct 2026: kinora as the case store; the registry dissolves

Scope discussion on "kinora replaces git, context registry as the case database, runs fully traceable, console exposes it". Outcome: no new component.

## Decisions

1. **The earlier prototypes' S3 context registry is not rebuilt.** Its three jobs are already kinora/moco concerns: bytes on S3 = the moco backend (RFC-0005, rustfs for dev); the SlateDB-style index = kinora's post-bootstrap cache index, kept as a *derived, rebuildable projection* (the orchestrator's rule carries over unchanged); pull/push sync = the store's own semantics (one file per event, set-union mergeable, put-once). Attachments (transcripts, screenshots) are moco blobs referenced from a kino; kura later. Not in the eight weeks unless the dogfood week demands it.
2. **"Kinora replaces git" means two specific things (YJ, 15 Oct, correcting an earlier reading):** (a) the **notes vault repo** — the git-backed home of cases (beans + State blocks), checks, watches, daily/weekly notes, memory files and WIP docs — is replaced by kinora stores as the long-term memory; a case becomes a context kino, a check or watch a kino with due/state metadata, a daily note a *rendered view* over the day's submissions rather than an authored file; (b) the **workflows in the earlier orchestrator** — the registry's plan/events/result run objects and the staged workflow engine over them — are replaced by kinora: a run is the sequence of submission kinos under a context, a workflow spec is itself a kino, stages (post-v1) are a layer of links over that. Code history stays in git; project `.kinora/` ledgers stay git-backed with their code. Migration of the vault and of the orchestrator's workflows is **post-v1**: v1 proves the substrate on the author's own work (phase 5); the vault switch is a separate "switch local tools to edger ones" decision. Gap to carry: the vault's private tier (age-encrypted notes) has no kinora equivalent; a personal S3 store is private by tenancy, but a shared workplace store would need an encrypted root.

3. **Layered stores.** A worker mounts two stores: the repo's ledger and the context store. A context cites project kinos by qualified id through *weak* metadata links. This is the cross-ledger reference RFC-0006 Q1 left open; the small new scope is a resolver over two stores and a link form that names the store. Weak, so nothing pins across stores and GC/retention stay per store.
4. **The one storage invariant (replaces "rewritten in place" in spec-context-unit):** a submission is a write-once kino with typed weak links (`context:`, `run:`, `session:`, `evidence:`…); the context's resume block is a superseded head that links back to the submission, never an edit. The supersedes chain *is* the history; backlinks *are* the trace.
5. **Views, not one model.** Three kinora primitives answer three readers and are not rivals: weak links → "what touched this context?" (worker, console query); supersedes → "what did it say last week?" (human, cold read); kinograph → "render this run as a page" (viewer, built later, never written by the worker). An orchestrator-style plan/events/result lineage is a view grouping submissions by run id until stages (post-v1) need a real seal. Per-context choice of view is allowed; storage does not change.

## Plan deltas

- Phase 2: submission = kino + links; resume block superseded; run id on every submission. Trace is free. Phase 2 settles the link vocabulary and the submission minimum (what established / what ruled out) against real use.
- Phase 3: unchanged in intent; wording: moco S3 backend, kinora index as rebuildable projection, context store mounted beside the project ledger (layered resolver). Multi-writer on S3 needs put-once as a conditional write.
- Phase 4: console gains a trace view, context → submissions → evidence, over resolver backlinks + supersedes walk. Face feature, no new engine call beyond what the resolver already exposes.
- Retention of superseded heads on S3: existing RootPolicy (Never / MaxAge / KeepLastN) per root.

## Open, carried

- Whether a worker's transcript is filed as a moco blob in v1 or only its distilled submission ("a session distills before it derives").
- Index shape: per store or across layered stores; rebuild cost on a phone.
- R2 conditional put (If-None-Match) semantics — verify first in phase 3; fallback exists-then-put under fork tolerance (see the moco backend section).
