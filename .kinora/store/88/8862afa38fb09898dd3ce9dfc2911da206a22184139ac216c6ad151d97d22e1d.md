# Finding, 23 Oct 2026: the second deployment's first real check run — what a worker's environment needs

Context: the second deployment (bundle 5) ran its first real due checks overnight on the deployed
build `8948da2`. All four were snoozed without a verdict: the workers reported that the chat,
issue-tracker, dashboard and search connectors were missing and that internal hosts did not
resolve. After the fixes below, a test check passed: the chat tools were present, a read from a
private channel returned a message, and the proxy variables were set. The four real checks come
due again later today.

## 1. `--strict-mcp-config` is hard-coded in the launch (upstream `552ee0c`, `kudo-worker/src/launch.rs`)

The launch now always passes `--strict-mcp-config`, so a worker gets kudo's MCP server and nothing
else. On the home lab that is a sensible default (fewer servers, fewer first-run prompts). For the
second deployment it breaks every check: each one reads the user's own MCP servers (chat, issue
tracker, dashboards, search), and strict mode drops all of them. Suggested shape, copied from the
existing "a node decides whether its workers bypass permissions" spec: a node opt-in variable
(for example `KUDO_WORKER_STRICT_MCP`), default as the author prefers, set on the node's own
environment and never sent by the console. The second deployment stays on `8948da2` until this
exists.

## 2. Connectors are not ready when the worker starts

The worker reported, in its own words, that the hosted connectors were "still connecting" at
session start and became usable a little later. The node's environment also lacked the proxy at
the time (finding 3), and both changed together, so which of the two caused the overnight misses
is not established. Either way, a worker must not conclude "no such tool" from a probe made
while connectors are still connecting. Options: the launch or the session-start hook waits until
the MCP servers have finished connecting before the kickoff prompt; or the worker instructions
say to re-probe (wait and retry) before snoozing or failing for a missing tool.

## 3. The node's environment is the workers' environment

A worker is a child of the node, so it inherits the node's environment, not the user's login
shell. A bare service environment (systemd user unit, launchd agent) has none of what the shell
sets. In the second deployment, outbound HTTPS goes through an authenticating proxy that injects
credentials, configured by a file the login shell sources, plus a CA bundle; none of it reached
the workers. Fixed by giving the node service that file as an `EnvironmentFile` and adding the
no-proxy list, the CA bundle variables (`SSL_CERT_FILE`, `NIX_SSL_CERT_FILE`) and the Node.js
ones (`NODE_USE_ENV_PROXY`, `NODE_EXTRA_CA_CERTS`). Worth a section in the deployment docs: what
the node's environment must carry, because it is what every worker sees.

## 4. Likely fixed upstream, to verify

On `8948da2` the waker logs "stopped pane … (never traced)" for the same long-gone pane on every
wake. Upstream `8fb14da` ("a gone pane holds no wake back") probably covers it; verify when the
second deployment updates.
